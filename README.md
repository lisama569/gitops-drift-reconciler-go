# gitops-drift-reconciler-go

一套**本地可运行**的期望状态收敛控制循环。用本地内存存储模拟期望声明与实际资源状态，
使差异计算、收敛执行以及并发触发下的结论一致、可解释且可复现。
整个验证过程不依赖任何外部服务、集群或凭据。

## 结构

```
internal/decl       期望声明的解析、校验与拓扑排序
internal/store      本地实际状态存储（乐观并发版本控制）
internal/plan       差异计算与有序变更计划
internal/reconcile  收敛控制循环（执行、失败分类、漂移处置、取消/超时、多实例并发）
cmd/reconciler      本地演示入口
```

## 计划与顺序语义

- **差异分类**：每个资源被判定为 `create`（实际缺失）、`update`（字段漂移，逐字段给出
  `旧值 -> 新值`）、`delete`（多余资源，期望声明中不存在）之一；无差异则不产生步骤。
- **执行顺序**：`create`/`update` 按依赖拓扑序排列（依赖在前），同层资源按 `kind/name`
  字典序；`delete` 一律排在最后，按 key 字典序。
- **可复现性**：同一份期望声明 + 同一份实际状态快照，必然得到完全相同的计划与顺序
  （所有迭代均先排序，无 map 遍历随机性）。
- **整体拒绝**：声明不合法（缺 kind/name、重复声明、依赖不存在的资源、依赖自身、依赖环）
  时，`Run` 直接返回 `validation` 错误，**不执行任何变更**，不会按部分内容继续。

## 收敛执行与幂等

- 执行严格按计划顺序推进；每个资源基于声明计算，已收敛的资源重复执行时计划为空，
  **不会产生额外变更或副作用**。
- 某一步失败时，执行**停留在该资源及其下游**：下游步骤标记为
  `dependency_not_ready`，其余未推进步骤一并记录，不再继续依赖链。
- 已完成资源保留在存储中，可通过 `store.Keys()` / `Snapshot()` 观察。
- 重试时重新计算计划：已完成的资源不再出现在计划中，只补齐剩余变更，
  最终收敛到与一次性成功**相同的结论**。

## 失败分类

| 类别 | 含义 |
|---|---|
| `validation` | 声明不合法 / 互相矛盾 / 依赖不存在，整体拒绝 |
| `dependency_not_ready` | 上游步骤失败，下游未就绪 |
| `conflict` | 写入时版本冲突（执行冲突） |
| `timeout` | 单步骤执行超过时限 |
| `drift_detected` | 计划生成与执行之间实际状态被外部改动，过期计划被拒绝 |
| `canceled` | 调用方通过 context 取消了本次收敛 |
| `execution` | 其他执行错误 |

## 多实例并发语义

- **独立实例共享存储**：可以创建多个彼此独立的 `Reconciler`（各自 `New(s)`）
  作用于**同一存储、同一期望声明**并发收敛。每个实例内部仍串行化自己的
  多次 `Run`，实例之间不互斥，真正并发。
- **同一资源最多下发一次**：存储的全局版本号提供乐观并发控制。两个实例基于
  同一快照竞争写入时，**只有一个成功**，其余得到明确的 `ErrConflict`
  （不会静默覆盖，也不会各自都以为成功）；冲突方若使用 `replan` 策略，
  会基于最新快照重新计算计划——已完成的资源不再出现在新计划中，
  因此不会重复下发。单次写入是整条记录的原子替换，不存在“只生效一半”
  的交错状态。
- **结论收敛**：实例数量增多、资源集放大、依赖链拉长之后，每个实例算出的
  计划仍只取决于（期望声明，实际状态快照），顺序稳定可复现；所有实例的
  最终结论收敛到同一个终态（测试中用“全局版本号 == 成功写入次数 ==
  期望资源数”断言每个资源恰好被下发一次，并比较两轮风暴的终态完全一致）。

## 漂移处置：两种方式怎么选

计划生成与执行之间实际状态被外部改动时，写入会因版本冲突被拒绝。
调用方通过 `RunContext(ctx, d, &Options{DriftPolicy: ...})` 选择处置方式：

| 策略 | 行为 | 适用场景 |
|---|---|---|
| `abort`（默认） | 拒绝过期计划，本次执行中止，`Drift=true`、失败原因 `drift_detected`，由下一次 `Run` 重新收敛 | 希望漂移显式可见、由外层调度节奏控制重试 |
| `replan` | 用最新实际状态重新快照、重新计算计划，接着往下收敛；已完成的步骤不重复下发，单次 `Run` 内最多重规划 32 次 | 多实例并发或外部变更频繁，希望单次调用内直接收敛 |

两种方式都保证**不会把过期计划套到已变化的资源上**（冲突写入一律被拒绝）。
`Result.Policy` 记录本次使用的策略，`Result.Replans` 记录每次重规划的
触发点、版本变化与原因，`Result.String()` 中均可观察。`Run(d)` 与
`opts=nil` 等价于 `abort`，与上一轮行为完全一致。

## 取消与超时的终态保证

- `RunContext` 接受调用方的 `context`：取消后当前步骤以 `canceled` 失败，
  被中断资源及其**下游停在原地**（下游标记 `dependency_not_ready`），
  已完成的部分保留在存储中、可观察可解释。
- `SetStepTimeout` 限制单步骤执行时限，超时以 `timeout` 失败，语义同上。
- **终态一致性**：存储写入只发生在运行 goroutine 内，且写入前会再次确认
  未取消、未超时；因此一旦本次执行被判定为失败，**之后不会再出现本次
  执行带来的任何写入**——结论必然等于最终实际状态，不存在“报告说失败、
  过一会儿资源又被改掉”的窗口。
- 重试（新的 `Run`）基于最新快照重新计算计划，只补齐剩余变更，
  最终收敛到与一次性成功相同的结论。

## 漂移与并发处理规则

- **版本化存储**：存储维护全局单调递增版本号，每次成功写入 +1。
  计划记录生成时的 `baseVersion`，执行时逐步携带版本写入（乐观并发）。
- **执行前漂移**：若计划生成后实际状态被外部修改，下一步写入会因版本冲突
  被拒绝；如何处置由调用方选择（见上文“漂移处置”），默认 `abort`。
- **并发触发**：同一 `Reconciler` 的多个 `Run` 在控制器层面串行化；
  多个独立 `Reconciler` 实例共享存储时靠版本号互斥（见上文“多实例并发
  语义”），同一资源不会被重复下发，也不会出现只生效一半的交错状态；
  每个循环都基于最新快照独立得出结论。

## 本地验证

```bash
# 全部单元测试（含竞态检测）
go test -race ./...

# 查看测试日志中的变更计划、依赖顺序、状态快照与判定依据
go test ./internal/reconcile/ -v

# 本地演示：连续两次收敛，第二次应为空计划（幂等）
go run ./cmd/reconciler
```

测试覆盖场景：

- `TestRepeatedRunIdempotent`：重复执行幂等，依赖顺序正确；
- `TestPartialFailureThenRetry`：部分失败后停留、下游标记 `dependency_not_ready`、
  重试收敛到同一结论且每个资源只下发一次；
- `TestConcurrentRuns`：8 个并发循环，每个资源全程只下发一次，最终状态一致；
- `TestDriftBetweenPlanAndApply`：计划与执行之间注入外部变更，过期计划被拒绝
  （`drift_detected`），重试后收敛；
- `TestFailureKindsDistinguishable`：`validation` 与 `timeout` 等失败原因可区分，
  非法声明不产生任何变更；
- `TestConcurrentCreateSameKey`（store）：16 个执行者并发创建同一资源，
  恰好 1 个成功、其余全部得到明确冲突；
- `TestMultiInstanceConcurrentStorm`：8 个独立实例共享存储并发收敛
  18 个资源（5 级长链 + 扇出），每个资源全程恰好下发一次、执行顺序满足
  依赖约束，两轮风暴终态完全一致；
- `TestDriftPolicyAbortExplicit` / `TestDriftPolicyReplan`：两种漂移处置方式
  各自的结论、报告与终态；
- `TestCancelStopsRunAndNoLateWrites` / `TestTimeoutNoLateWrites`：取消与超时
  判定失败后不再出现迟到写入，重试收敛到同一结论。

测试日志（`go test ./internal/reconcile/ -v`）会打印每轮算出的变更计划、
执行顺序、重规划事件、中间与最终状态快照以及每条结论的判定依据。
